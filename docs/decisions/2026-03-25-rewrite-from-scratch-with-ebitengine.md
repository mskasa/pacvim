# 0001: termbox 版を廃止し Ebitengine で1から書き直す

- Date: 2026-03-25
- Status: Active
- Author: mskasa

## Context

PacVim は `github.com/nsf/termbox-go` を使ったターミナルゲームとして実装されていた。
この実装には構造的な問題があり、機能追加のたびにコストが増大していた。

最大の問題は **termbox のセルバッファをゲーム状態として流用していた** ことである。
座標 `(x, y)` の状態を知るには `termbox.CellBuffer()` を直接読む必要があり、
`isCharApple(x, y)` のような判定関数がすべて描画ライブラリに依存していた。

結果として以下の問題が生じていた。

- 状態と描画が不可分のため単体テストが書けない
- 新しい Vim コマンドを追加するたびに描画レイヤーに依存したコードが増える
- termbox はターミナル前提のため WebAssembly ビルドができない
- スプライト・アニメーション・サウンドなど表現力を広げられない

既存コードを Ebitengine に移行する方法も検討したが、
termbox への依存が `player.go` / `buffer.go` / `stage.go` / `enemy.go` の全体に
深く染み込んでおり、移行コストと新規作成コストがほぼ同等であると判断した。
また移行アプローチでは「古いコードの文脈を引きずった中途半端な設計」になるリスクがあった。

## Decision

既存の Go ファイルをすべて削除し、Ebitengine を前提とした設計で1から書き直す。

作業は既存リポジトリの `ebitengine` ブランチ上で行う。
マップファイル（`files/stage/*.txt`）は書式・内容ともに再利用する。
実装完了後に `main` ブランチへマージする。

## Consequences

**得るもの**

- `state` パッケージを ebiten から切り離すことで単体テストが書けるようになる
- WebAssembly ビルドが可能になりブラウザで動作させられる
- クリーンな設計基盤の上で Vim コマンドを安全に拡張できる
- スプライト・SE など表現力を高められる

**失うもの・トレードオフ**

- ターミナル上でシンプルに動く軽量さは失われる
- SSH 環境では動作しない（Ebitengine はウィンドウを開く）
- 書き直しの工数がかかる

## Alternatives Considered

**既存コードを段階的に Ebitengine へ移行する**
termbox 依存がコード全体に染み込んでおり、移行コストと新規作成コストがほぼ同等。
移行アプローチでは古いコードの文脈が残り、設計が歪む可能性があった。

**termbox のまま維持し機能追加を続ける**
工数は最小だが、テスタビリティの問題と WebAssembly 非対応が解決しない。
Vim コマンドを追加するほどコードが複雑化する構造的問題も残る。

**別の TUI ライブラリ（bubbletea / tcell）に移行する**
TUI ライブラリを変えても状態と描画の分離問題は解決しない。
WebAssembly 対応もできないため、Ebitengine への移行と比べてメリットが薄い。
